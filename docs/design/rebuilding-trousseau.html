Engineering plan

Rebuilding Trousseau

Keep the idea, an encrypted key-value file you can hand to someone. Replace everything under it: age instead of OpenPGP and unauthenticated AES, Rust instead of Go, and a product aimed at developers who want secrets next to their code without running a server.

Prepared for Théo Crevon, owner Basis oleiade/trousseau at master (2026-02-08), motus conventions Date 2026-09-12

Recommendation in one screen

Rebuild from scratch. Do not port. The Go code is 4,146 lines of 2013-era architecture with global state and exits inside library code, and its two encryption paths are both unfit: one is unauthenticated, the other no longer works with any GnuPG shipped in the last decade.

  1. 1Adopt the age format as the envelope. It gives multi-recipient encryption, a passphrase mode, SSH keys as recipients, and hardware keys through plugins. It also means a store can be recovered with the age tool alone if trousseau ever disappears.
  2. 2Reposition as a git-friendly secrets file for developers and small teams. The unit becomes a project-local .trousseau file committed to the repo, plus one personal store. The headline feature is trousseau run, which injects secrets as environment variables into a child process.
  3. 3Cut OpenPGP, the S3/scp/gist remotes, and the "bank details and bitcoin wallets" audience. Password managers won that market. Remotes are auth surface and dependency weight for a problem git and rsync already solve.
  4. 4Ship a read-only migrator for v0.4 stores so the 956-star user base can move in one command, then never carry the legacy code forward.
  5. 5Reuse the motus toolchain: Cargo workspace, edition 2024, pedantic clippy, forbid unsafe, cargo-deny, GoReleaser with cargo-zigbuild, Homebrew tap and the oleiade apt repository. Add build provenance attestations and a paid crypto review before 1.0.
  6. 6Budget roughly 10 to 12 weeks of focused work to 1.0, in four milestones with exit gates. The scope discipline matters more than the schedule. Breadth is what killed the first version.

Positioning and audience

The 2013 README pitched three audiences at once: ops sharing certificates across a cluster, teams sharing service passwords, and individuals storing bank details. Pick one. The other two are served by products with far more resources.

Who it is for

Primary: individual developers and teams of two to twenty who keep a project's secrets in the repository, next to the code, with no server to run and no subscription to buy. The concrete job is "replace the .env file I am not supposed to commit."

Secondary: operators who bootstrap machines. With age, an SSH public key is a valid recipient, so "encrypt this store for these three servers" needs no key ceremony. That is the original cluster use case, finally without GnuPG.

Not for: humans storing personal passwords (1Password, Bitwarden, KeePassXC), organizations needing audit logs, dynamic secrets, or access policies (Vault, Infisical, Doppler, cloud secret managers), or anyone who wants a GUI.

One-line position

An encrypted key-value file you can commit, share with people and machines, and run your program with. No server, no account, recoverable with age alone.

Keep, cut, add, change

Keep

  • Single encrypted file as the unit of storage and sharing
  • Key-value model, get/set/list/remove
  • Two access modes: recipients, or a passphrase
  • Recipient management on the store itself
  • Plain export and import with a merge strategy
  • The name and the repository

Cut

  • OpenPGP and every GnuPG integration
  • S3, scp and gist push and pull
  • DSN syntax with embedded credentials
  • Secret values on the command line
  • OS keyring lookup of the passphrase
  • The personal password manager pitch
  • The in-place upgrade chain for 0.3.x formats

Add

  • run: inject secrets as env vars into a child process
  • env: print in shell, dotenv or JSON form for direnv and CI
  • edit: full round trip in $EDITOR
  • Project-local stores discovered like .git
  • SSH keys and hardware keys as recipients via age
  • Hierarchical keys, binary values, per-entry metadata
  • --json on every read command
  • Clipboard copy with timed clear
  • A stable library crate

Change

  • Envelope: age instead of bespoke AES and PGP
  • Payload: versioned JSON schema instead of a bare map
  • Writes: temp file, fsync, rename, advisory lock
  • Identity: age identity or SSH key file, never an env var passphrase by default
  • Verbs: del becomes rm, keys becomes ls, create becomes init
  • Config and data under XDG paths

Cryptography: build on age

The single largest decision. Three options were on the table. The recommendation is the age format through the Rust age crate, the library behind rage.

OptionForAgainstVerdict
age format via the age crateReviewed public spec since 2019. Multi-recipient X25519, scrypt passphrase mode, ssh-ed25519 and ssh-rsa recipients, plugin protocol for YubiKey, Secure Enclave, TPM and FIDO2. Payload is ChaCha20-Poly1305 in authenticated 64 KiB chunks, header is MAC'd. KDF cost is stored in the header. Emergency recovery with age -d. Interoperates with sops and passage users' existing identities.The crate is pre-1.0 (0.11.x). No sender authentication: any recipient can produce a valid file. A passphrase recipient cannot be mixed with other recipients in the same file. No public third-party audit of either implementation that I can point to.Recommended
Bespoke envelope: Argon2id, XChaCha20-Poly1305, X25519 key wrappingFull control. Could add signatures and mixed recipient sets from day one.Every reviewer's first question will be "why not age". Own spec, own test vectors, own audit, own plugin story for hardware keys. Zero interoperability. This is the path the 2013 version took and it aged badly.Reject
OpenPGP via sequoia-openpgpContinuity with existing recipients. Sequoia is a serious, audited Rust implementation. Signatures come built in.GnuPG key management was the reason the old asymmetric mode rotted. The PGP UX problem is the product problem. Large dependency surface.Reject for v1

Consequences you should know before saying yes

  • Passphrase stores and recipient stores stay separate kinds, exactly as today's symmetric and asymmetric split. Converting between them is a rekey, which is cheap because the payload is small.
  • Every save re-encrypts under a fresh file key. Removing a recipient therefore takes effect on the next write. They keep whatever git history they already have, which is true of every scheme.
  • No signatures in v1. Within a team of recipients, tampering is not detectable by cryptography, only by git history. Document it. An optional ed25519 detached signature is a v1.x candidate.
  • SSH keys as identities work from the private key file, with a passphrase prompt if it is encrypted. Keys that live only in an agent (1Password's SSH agent, FIDO security keys) cannot decrypt. The fallback is a generated age identity, which init creates in one step.
  • Hardware keys arrive through the plugin protocol, not through code in trousseau. That closes #187 with documentation instead of an integration to maintain.
Audit

Budget a short external review of the format bindings and the CLI's handling of secrets (argv, env, temp files, clipboard) before 1.0, the same way motus has an audit/ directory. The primitives are not where a tool like this fails. The plumbing around them is.

Store format

One ASCII-armored age file. Inside it, one versioned JSON document. Nothing else on disk belongs to the store.

  • Armored, so the file diffs as text in git and survives copy-paste. Detection is trivial: the file starts with the age armor header, the way 0.3.0 stores were detected by the PGP header.
  • Recipient list lives inside the encrypted payload. Any recipient can re-encrypt on write. The age header does not reveal X25519 recipient identities, so the file leaks only the recipient count.
  • Keys are paths. database/password, stripe/webhook-secret. ls takes a prefix. This is the answer to #192 without a nested document model.
  • Values are bytes with an encoding tag, so a certificate or a binary key file round-trips through set --from-file and get --out.
  • Per-entry metadata: description, timestamps, and an explicit environment variable name that overrides the default mapping. This is #193, scoped to what run needs.
  • Schema version in the payload. Readers refuse newer majors with a clear message instead of guessing.
{
  "schema": 1,
  "created_at": "2026-09-12T09:41:00Z",
  "updated_at": "2026-09-12T10:02:13Z",
  "recipients": [
    "age1ql3z7hjy54pw3hyww5ayyfg7zqgvc7w3j2elw8zmrj2kg5sfn9aqmcac8p",
    "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIL... deploy@web-01"
  ],
  "entries": {
    "database/password": {
      "value": "s3cr3t", "encoding": "utf8",
      "env": "DATABASE_PASSWORD",
      "description": "Postgres app role",
      "created_at": "...", "updated_at": "..."
    },
    "tls/server.key": { "value": "LS0tLS1CRUdJTi...", "encoding": "base64" }
  }
}

Default environment mapping: uppercase, with / and - replaced by _. database/password becomes DATABASE_PASSWORD without anyone configuring anything.

Selection order for the store: --store, then TROUSSEAU_STORE, then the nearest project store, then the personal store. The same precedence, stated once in the docs, is what stops the "which store did I just write to" class of bug that #112 was.

Command line

Four rules, then the verbs. Secret values never appear on the command line. Every read has --json. One store per invocation, chosen by one precedence rule. Nothing is interactive when stdin is not a terminal.

Identity and passphrase resolution

In order: --identity PATH, TROUSSEAU_IDENTITY_FILE, identities listed in config, the default identity file, then ~/.ssh/id_ed25519 and ~/.ssh/id_rsa. For passphrase stores: prompt, or --passphrase-file. TROUSSEAU_PASSPHRASE survives only for CI, prints a warning on a terminal, and is documented as the wrong tool. CI should use an identity file written from a CI secret, which is how sops and age users already work.

Global flags

--store, --global, --identity, --json, --quiet, --no-input. That is the whole list. --ask-passphrase, --gnupg-home and --verbose go away.

Threat model, stated plainly

The old README never said what the tool defends against. The new one does, in the first screen. This is the version to sign off on.

Defends against

  • Disclosure of the store at rest: stolen laptop, leaked bucket, public repository, synced folder
  • Undetected modification of the store by a non-recipient
  • Secrets in shell history, process lists, and crash logs via argv
  • Downgrade of KDF cost, because cost is bound in the header
  • Partial writes and concurrent writers corrupting the store

Does not defend against

  • A compromised host while an identity is usable there
  • A malicious recipient rewriting the store (no signatures in v1)
  • The child process of run leaking its own environment
  • Secrets paged to swap: v1 zeroizes on drop but does not lock memory
  • Editors that leave backup or swap files during edit: documented, with the right flags for vim and VS Code
  • Clipboard managers that keep history

Migration from v0.4

A rebuild with a new file format is only acceptable if existing users move in one command. The migrator is read-only, lives in its own module, and is deleted at 2.0.

  • Detection: a JSON object with crypto_type, crypto_algorithm and _data keys. That is exactly today's version discovery.
  • Symmetric stores: reimplement the legacy decrypt only: scrypt with the fixed parameters, then AES-256-CFB. About forty lines, with a fixture generated by the current Go binary so it is tested against reality.
  • OpenPGP stores: shell out to gpg --decrypt on the armored payload. Never parse a keyring again. If the user's GnuPG cannot decrypt it, trousseau could not have either.
  • Output: a v1 store encrypted to the identities the user names on the command line. Recipients from the old store are shown but not carried, since PGP key ids are not age recipients.
  • Keep the old file. The migrator never deletes or overwrites the source.

Release engineering

Reuse the motus pipeline as is: GoReleaser with cargo-zigbuild for Linux x86_64 and aarch64 and macOS, Homebrew tap, the oleiade apt repository, cargo-deny on a daily schedule, Renovate. Windows builds are worth shipping since nothing in the stack blocks them, with the clipboard and plugin caveats noted in the docs.

Add three things motus does not have yet, all cheap:

  • Build provenance through GitHub artifact attestations on every release asset, so a downloaded binary can be traced to a workflow run and commit.
  • An SBOM per release, generated from Cargo.lock.
  • A security policy file with a disclosure contact and a stated support window.

Retire the hand-written completion scripts and the Vagrant provisioning script. Keep MIT unless you want AGPL like motus; that is a decision for you below, not for me.

Roadmap

Four milestones, each with a gate you can check. Durations assume one engineer at roughly full focus. Sequence matters more than the dates.

  1. Weeks 1 to 2
    M0. Decide and specify

    Sign off on the decisions below. Write the format spec, the CLI reference, and the threat model as documents in the repo before code. Build a throwaway age round-trip to confirm plugin and SSH identity behavior on macOS and Linux.

    The three documents are merged, and a spike decrypts a file with an SSH key, an age identity, and a YubiKey plugin.

  2. Weeks 3 to 8
    M1. Core library and CLI

    Library crate with the schema, store I/O, locking and the age bindings. CLI with init, set, get, ls, rm, mv, recipients, rekey, run, env, edit, export, import, info. JSON output everywhere. Property tests and fuzz targets in CI from the first week.

    A project store round-trips through every command on the three platforms, and age -d alone recovers it.

  3. Weeks 9 to 10
    M2. Migration, packaging, docs

    The v0.4 migrator with fixtures from the Go binary. Release pipeline, attestations, SBOM, Homebrew and apt. A README that leads with run, states the threat model, and shows the git workflow.

    A 2019-era store migrates on a clean machine, and a tagged release publishes to all channels without manual steps.

  4. Weeks 11 to 12
    M3. Review and 1.0

    External review of secret handling and format bindings. Fix what it finds. Publish 1.0 with a migration guide and an announcement aimed at sops, dotenvx and pass users.

    Review findings closed or accepted in writing. 1.0 tagged.

  5. After 1.0
    Candidates, not commitments

    Optional detached signatures for tamper evidence between recipients. A short-lived identity cache backed by the OS keychain. A published, semver-stable library API. Nothing with a server in it.

Decisions that are yours

Each one has a recommendation. Where you disagree, the plan still holds; the affected milestone just changes shape.

D1Envelope formatage

TradeInteroperability, hardware keys and a reviewed spec, against a 0.x crate and no signatures. Choosing bespoke costs an extra milestone and an audit with a much wider scope.

D2Store scopeProject-local plus one personal store

TradeThis is the positioning change. The alternative, one home store as today, keeps the old audience and forfeits the "commit it" story that differentiates the tool.

D3Remote storageRemove entirely

TradeA few users will miss push s3://. The AWS SDK alone was more than half of the old dependency tree, and the remotes produced the two worst security findings. If demand shows up, an S3 target can return as an optional feature in 1.x.

D4Passphrase and identity cachingNone in 1.0

TradeUsers with a passphrase-protected identity type it per command, like ssh without an agent. An agent or keychain cache is a well-understood 1.x addition and a poor thing to design under 1.0 pressure.

D5Payload modelFlat path keys with per-entry metadata

TradeA nested document model (what sops does) would make trousseau a config encryptor. Path keys deliver sections and stay a key-value store.

D6Legacy supportRead-only migrator, deleted at 2.0

TradeNo dual-format support, ever. Carrying two formats is how the 0.3 upgrade closures ended up in the tree.

D7LicenseYour call

TradeMIT keeps continuity with 13 years of contributors and eases adoption in company repos. AGPL matches motus and your current stance. A rewrite is the one moment a change costs nothing legally, since no old code is carried over.

D8Versioning and nameSame repository, 1.0.0, new format

TradeThe name and stars are the asset. A new name starts from zero. The Go tree moves to a legacy branch with a final tag.

D9External reviewYes, scoped, before 1.0

TradeA few days of a specialist's time. Skipping it is defensible for a hobby release and not for a tool whose README says "secure".
